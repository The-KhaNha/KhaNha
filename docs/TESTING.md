# Testing

Both packages use [Vitest](https://vitest.dev). The server drives the real Express app with Supertest against a real
Supabase database. The client runs unit tests in jsdom with Testing Library.

## Running

```bash
# server/ — needs the local Supabase stack running and seeded
cd server
pnpm run db:start          # once per boot (Docker)
pnpm run seed              # demo store, menu and test accounts
pnpm test                  # vitest run (the S3 store's cases skip unless RustFS runs: docker compose up -d media)
pnpm run test:watch

# client/ — no backend needed
cd client
pnpm test
pnpm run test:watch
```

The full gate for a touched package is `pnpm run typecheck && pnpm run lint && pnpm test`.

## The test-target guard (server)

`server/test/setup/guard.ts` runs before any test file imports the app. It calls `resolveTestTarget()` from
`test/setup/target.ts`, which decides which Supabase project the run may touch:

| `TEST_TARGET`     | Allowed when                                                                                            | Suites that run       |
| ----------------- | ------------------------------------------------------------------------------------------------------- | --------------------- |
| `local` (default) | `APP_ENV=local` and `SUPABASE_URL` host is `127.0.0.1`/`localhost`                                      | every `*.test.ts`     |
| `staging`         | `ALLOW_STAGING_TESTS=1`, `APP_ENV=staging`, `TEST_STAGING_HOST` set, and `SUPABASE_URL` host matches it | only `*.safe.test.ts` |
| `production`      | never                                                                                                   | –                     |

If the guard throws, the whole run stops before a single request is made. `vitest.config.mts` loads `server/.env` before choosing which files to include, so the file filter and the guard always read the same `TEST_TARGET`. Production is never a test target.

## Destructive vs staging-safe suites

- A suite is **staging-safe** when it only reads shared data, or creates its own data and removes it in
  `afterAll`. Name the file `*.safe.test.ts`.
- Anything else (it calls `resetDemoData()`, changes shared stock or the store, or leaves orders behind) is
  **destructive**. Name it `*.test.ts`. Destructive suites run on local only.

## Table ownership

`server/eslint.config.mjs` keeps `TABLE_OWNERS`, a map from each store-scoped table (`orders`, `order_items`,
`menu_items`, `store_memberships`, `store_invites`, `domain_events`) to the source files allowed to query it with `.from('<table>')`.
`pnpm run lint` fails anywhere else under `server/src/`, so a table's store filter and its 404 rule stay in its owning
service and other modules call that service. `store_memberships` and `store_invites` belong to `src/services/team.service.ts`. An empty list means no file may query the table yet (`domain_events`). A new store-scoped
table gets a row in the same change. Tests and scripts are exempt; they set up fixtures directly.
`test/unit/table-ownership.safe.test.ts` proves the rule fires.

## Helpers (`server/test/setup/helpers.ts`)

- `createTestUser(role?)` creates a confirmed user through the admin API, promotes the profile only for `ADMIN` (the trigger
  always makes a CUSTOMER) and signs in; `'STAFF'` is a CUSTOMER profile that is also a STAFF member of the oldest store (`STAFF` is a membership role only). It returns `{ id, email, password, token }`. Send the token as
  `Authorization: Bearer <token>`.
- `createStoreMember(storeId, role)` creates a customer account and a `store_memberships` row for it; `createBrandOwner(brandId)` makes a new account the owner of a brand the test created. Both return the `createTestUser` shape.
- `deleteTestUser(user)` deletes the auth user; the profile goes with it through the cascade. Call it in `afterAll`.
- `testStoreIsolation(label, send, resource?)` is the tenant matrix every store route runs (P2.3), on two stores of
  two brands it makes: store A's staff on store B's route 403, A's staff reaching B's resource through A's route 404
  (when the route addresses one: `resource(storeId)` makes it), the other brand's owner 403, a customer 403, anonymous
  401, and A's staff on A's own route through. `deleteTestStores(storeIds, brandIds, users)` removes a test's own
  stores with their events and orders.
- `testAuthMatrix(...)` runs the shared 401 cases (no header, malformed scheme, foreign JWT, deleted user) against a
  route; `foreignJwt()` makes a well-formed JWT with a random signature (fails JWKS verification like a foreign or tampered
  token); `deleteAccountByEmail(email)` removes an account a test
  registered.
- `resetDemoData()` runs `scripts/seed.ts`. That wipes every order through `reset_demo_orders` and restores the
  store, the menu (including stock) and the two demo accounts. It refuses to run unless the target is local.
- `localSql(sql)` runs one row-returning statement as `postgres` (`supabase db query`, local by default) for what the API
  cannot reach: pgmq, `cron.job`, the catalogs. Local only. `test/api/database-lockdown.test.ts` uses it to check
  every table, function and queue schema is closed to `anon` and `authenticated` (SCHEMA.md "Row-level security").

### The per-file API server

`server/test/setup/api.ts`:

Every suite calls `api()` (a Supertest client), never `request(createApp())` directly:

- `request(createApp())` makes Supertest listen on every interface (`::`) but connect to `127.0.0.1`. On macOS,
  another local process already bound to `127.0.0.1` on that same random port wins the connection, so the test's
  request silently gets a stranger's reply — seen as a foreign 404 or an "Invalid authentication" body, roughly 1 run
  in 10.
- `test/setup/api.ts` instead starts one real server per test file, bound to `127.0.0.1` itself
  (`createApp().listen(0, '127.0.0.1')`), so there is nothing else it could connect to. `test/setup/guard.ts` calls
  `startApi()` in `beforeAll` and `stopApi()` in `afterAll`; a suite that calls `api()` before `guard.ts` has run
  gets a clear thrown error instead of a hang.
- All suites under `test/api/` use `api().get(...)` / `.post(...)` / etc.; none import `createApp()` or `supertest`
  directly.

### One run at a time (`server/test/setup/run-lock.ts`)

All test runs share the local Supabase database, and a destructive suite reseeds it (`resetDemoData()`), which wipes
every non-demo account — including a parallel run's test users, whose requests then fail with 401. A `globalSetup`
therefore takes a file lock (`<tmpdir>/food-pickup-server-tests.lock`) before any suite runs and releases it after;
a second concurrent `pnpm test` waits (up to 5 minutes) instead of corrupting the first run's data. A lock left behind
by a crashed run is detected (its pid is gone) and cleared automatically.

The response shapes in `server/src/types/api.ts` (`XDto`) and `client/src/types/api.ts` (`X`) are kept in sync by
hand. The `test-generator` agent compares them field by field, and endpoint tests assert the real response bodies
against them. `ErrorCode` exists only on the server (`server/src/utils/errors.ts`); the client treats
`ApiError.code` as a string.

A test that fails because of a real bug is a bug report. Never weaken the assertion to make it pass.

## Continuous integration

The root `pnpm test` also runs `scripts/codex/compat.test.mjs`: skill/role discovery parity, destructive-git denials,
patch-based reuse reminders, prompt and advisory Stop output, and local plugin scope/resource resolution. The tests
use temporary fixtures and never start application services. Runtime setup and hook trust are in [CODEX.md](CODEX.md).

`.github/workflows/ci.yml` runs on every pull request into `main` (production), `dev` (staging) or a `feat/**` branch
(development: a phase feature branch, CLAUDE.md §21), and on every push to `main`, `dev` and the phase branches
(`feat/P<n>`). The push run on a phase branch catches two PRs that were each green alone but break together once both
are merged; a push to a work branch gets no run of its own, since its PR run covers it. Every job that needs pnpm sets it up
through the local `.github/actions/setup-pnpm` action: Node from `.node-version`, `corepack enable` on that Node (the
runner's default Node carries an older corepack that cannot run pnpm 12), then the pnpm store cache keyed on the
job's `pnpm-lock.yaml`. Its aggregate
job `ci-ok` sums them up, and the `ci-ok required` ruleset blocks a merge into `main`, `dev` or a listed phase branch
until it is green ([ADR-011](adr/011-free-tiers.md)). It fails when any job failed or was cancelled, and counts
skipped jobs as passed. The workflow has no `paths:` filter, so every PR reports `ci-ok`; inside it the `changes` job
(`dorny/paths-filter`) skips what a PR does not touch, which keeps a PR's run short:

| Changed                                         | Jobs that run (besides `changes`, `repo`, `version-intent` on PRs, `ci-ok`) |
| ----------------------------------------------- | --------------------------------------------------------------------------- |
| `client/**`                                     | `client`, `images`                                                          |
| `server/**`, `client/src/config/fallbacks.json` | `server-static`, `server-tests`, `migrations` (PRs), `images`               |
| `compose.yaml`                                  | `images`                                                                    |
| `.github/workflows/ci.yml`, `.node-version`     | all of them                                                                 |
| only docs, plans, `scripts/**`, `.claude/**`    | none                                                                        |

Roughly: a docs-only PR costs 4–5 billed minutes a push, a client change about 12, a server change about 20 (most of it
`server-tests` starting Supabase). Each job is billed rounded up to a whole minute.

reads `client/dist/.vite/manifest.json`, sums the entry chunk and its static imports at gzip level 9, prints a table
(lazy chunks listed for information) and exits 1 when over.

`server-tests` runs the whole server suite, destructive tests included, against a throwaway local stack. Expect 8–10
minutes for the workflow: the Supabase image pulls take 2–4 minutes and the tests 1–3. `db:start:ci`'s `-x` list names
the CLI's containers, which change between CLI versions (check `pnpm exec supabase start --help` after a CLI bump).

Dependabot (`.github/dependabot.yml`) opens weekly grouped minor/patch PRs into `dev` for both packages, GitHub
Actions and the Dockerfiles, labelled `dependencies` and `no-release`, for versions at least 7 days old (`cooldown`;
security updates are not delayed). Every action is pinned to a commit SHA with its version in a comment, which
Dependabot keeps current: a tag can be repointed, a SHA cannot. Each root's `pnpm-workspace.yaml` sets
`minimumReleaseAge: 10080` (minutes), so an install never resolves a version published in the last week (a hijacked
release is usually caught by then), and `strictDepBuilds` with `allowBuilds` keeps every dependency install script
from running: one not listed fails the install. `scripts/ci/package-manager.test.mjs` (root `pnpm test`) guards these
settings, the one pinned pnpm and the absence of npm commands.

Validate a workflow change with `docker run --rm -v "$PWD":/repo -w /repo rhysd/actionlint:latest -color`.

`release.yml` is not a check: it opens the release PR (`workflow_dispatch`) and, after the merge into `main`, tags
the versions and opens the back-merge PR into `dev` (CLAUDE.md §21).

### Lighthouse (`perf.yml`)

On pushes to `dev` that touch `client/**` (one run per merged client PR) and on demand (`workflow_dispatch`, before
a release); informational. About 12 minutes a run, so it does not run on every PR push (ADR-011). It starts local Supabase
(`db:start:ci`, seed), brings up `docker compose up --wait web api`, runs `pnpm dlx @lhci/cli autorun` in `client/` with
`client/lighthouserc.json` (`/` and `/menu`, 360×640, Slow 4G, 4× CPU, three runs; LCP, CLS and TBT budgets as
warnings) and uploads `client/lhci/` as the `lighthouse-report` artifact. Numbers: `docs/PERF_BASELINE.md`
"CI numbers".

### WebKit smoke (`browsers.yml`)

Weekly (Monday 03:30 UTC) and on demand; informational. Installs WebKit with its system libraries and runs
`pnpm run e2e:webkit` (every spec in `client/e2e/`: home, menu, add to cart, cart at 360px, no sideways scroll,
clean console, every `/api` call mocked). Failure screenshots are uploaded as `webkit-smoke`. Locally,
`pnpm run e2e:chromium` runs the same specs on Chromium where WebKit cannot launch (WSL without its libraries).

### Security checks (`security.yml`)

Runs weekly (Monday 03:00 UTC), on demand, and on PRs into `main`, `dev` or a `feat/**` branch that change a `package.json`,
a `pnpm-lock.yaml`, a `pnpm-workspace.yaml`, the `setup-pnpm` action, a Dockerfile, `client/nginx/` or `.gitleaks.toml`. These results are advisory, not
merge-blocking: the `ci-ok required` ruleset requires only `ci-ok`, which does not depend on this workflow, so a red
`audit` or `images` on a PR leaves `ci-ok` green and the PR mergeable. Read them before merging and do not merge on red
(CLAUDE.md §13). A new advisory in an unchanged dependency does not touch unrelated PRs: the weekly run fails and
Dependabot raises the alert. What does block a merge, through `ci-ok`, is a PR's own commits scanned for secrets by
`ci.yml`'s `repo` job on every PR, and its code by `static-analysis`.

| Job       | Runs                                                                                                                                                                                                                          | Reproduce locally                                                                                                                                |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `audit`   | `pnpm audit --audit-level moderate` (it reads the lockfile; nothing is installed) in the root, `client/` and `server/`: every dependency, dev tooling included (a compromised build tool reaches the bundle and CI's secrets) | the same command in each package                                                                                                                 |
| `images`  | builds `fp-api` and `fp-web` and runs `trivy image --scanners vuln --ignore-unfixed --exit-code 1` on each: OS packages and Node modules as they would ship (a CVE with no fix yet cannot be acted on)                        | `docker build -t fp-api:scan server && docker build -t fp-web:scan client`, then the same `trivy image` line                                     |
| `secrets` | the gitleaks binary over every branch's full history (`--log-opts="--diff-merges=first-parent --all"`: the repository is public), `--redact`, with `.gitleaks.toml`                                                           | `docker run --rm -v "$PWD":/repo -w /repo zricethezav/gitleaks:v8.30.1 detect --source . --redact --log-opts="--diff-merges=first-parent --all"` |

Both gitleaks scans pass `--diff-merges=first-parent`: gitleaks reads `git log -p`, which prints no patch for a merge
commit, so a secret added only in a merge's conflict resolution would never be scanned. `-m` would report it once per
parent, and on a PR (checked out as a merge of the base and the PR) would rescan what the base gained since the fork; the
first-parent diff reports it once and covers only the PR's own changes. `scripts/ci/gitleaks-merge-diffs.test.mjs` fails
when a workflow's gitleaks call drops the option.

`.gitleaks.toml` extends the default rules and allowlists by value only: Supabase publishable keys, the CLI's fixed
local secret in `server/.env.example`, and two fakes the scrubber test feeds in (`server/test/api/client-errors.safe.test.ts`).
A real key anywhere else, `.env.example` included, still fails. Scheduled runs use `main`'s copy of a workflow, so the
weekly run starts once the first release brings this file to `main`. CodeQL is not run: it
needed GitHub Code Security while the repository was private, and is not set up yet (ADR-011).

### Break testing (`/break`)

Not a CI job: the `app-breaker` agent (`.claude/agents/app-breaker.md`) is run through `/break` before a release
and after a change to auth, orders, money or the request pipeline. Four groups (`security` at effort `xhigh`,
`data`, `flow`, `env`) attack the local servers with curl, throwaway scripts and the Playwright browser: secrets
in the built bundle and history, direct API calls logged out or as someone else, tampered prices and roles, floods
(the rate limits), stored script in names and notes, missing headers, a menu past `MENU_ITEMS_MAX`, long emoji
names, email capitalisation, empty forms, double submit with and without an `idempotencyKey`, refresh mid-form,
saves while offline, dead buttons, text at 200%, the WebKit smoke, time zones and a throttled golden path. Every
BREAK comes with a repro, evidence and a fix; what cannot be tested is listed as untested with the reason. Read-only
for source; the main session fixes and re-runs the failed group.

### Staging tests (later)

Not set up yet. When they are, a workflow sets `TEST_TARGET=staging`, `ALLOW_STAGING_TESTS=1`, `APP_ENV=staging`,
`TEST_STAGING_HOST` and the staging `SUPABASE_URL` / `SUPABASE_SECRET_KEY` from repository secrets, then runs
`pnpm test` in `server/`. The config then picks up `*.safe.test.ts` only.
